### Auth.js (installed: `next-auth@5.0.0-beta.32`, `@auth/core@0.41.3`) — verified from `node_modules/.pnpm/...` sources, not training memory

**Resend provider** (`@auth/core/providers/resend.js`, re-exported by `next-auth/providers/resend`):
```js
export default function Resend(config) {
  return {
    id: "resend", type: "email", name: "Resend",
    from: "Auth.js <no-reply@authjs.dev>", maxAge: 24*60*60,
    async sendVerificationRequest(params) {
      const { identifier: to, provider, url, theme } = params;
      const { host } = new URL(url);
      const res = await fetch("https://api.resend.com/emails", {
        method: "POST",
        headers: { Authorization: `Bearer ${provider.apiKey}`, "Content-Type": "application/json" },
        body: JSON.stringify({ from: provider.from, to, subject: `Sign in to ${host}`, html: html(...), text: text(...) }),
      });
      if (!res.ok) throw new Error("Resend error: " + JSON.stringify(await res.json()));
    },
    options: config,
  };
}
```
Plain HTTP `fetch` — works unmodified on Cloudflare Workers, no SMTP. `provider.from` must be set (either in config or left at the `no-reply@authjs.dev` default, which Resend will reject for an unverified domain in production).

**Env var auto-wiring** (`@auth/core/lib/utils/env.js::setEnvDefaults`, confirmed by reading the function body): for a provider with id `resend`, `ID = "RESEND"`, and it reads `envObject["AUTH_RESEND_KEY"]` into `provider.apiKey` automatically — **exactly the `AUTH_RESEND_KEY` convention already assumed**, and it is the *same* mechanism the current Discord provider relies on for `AUTH_DISCORD_ID`/`AUTH_DISCORD_SECRET` (`clientId`/`clientSecret` via `AUTH_${ID}_ID`/`AUTH_${ID}_SECRET`). `next-auth/lib/env.js::setEnvDefaults` calls `coreSetEnvDefaults(process.env, config, true)` — i.e. it always reads `process.env`, the same `process.env` the existing Discord wiring already depends on under Cloudflare/OpenNext. **No new env-wiring mechanism is needed** — `AUTH_RESEND_KEY` in `.dev.vars`/wrangler secrets will "just work" the same way `AUTH_DISCORD_ID` already does. There is **no** auto-wired env var for `from`/sender domain — that must be set explicitly in the provider config (e.g. `Resend({ from: "Become a Legend <noreply@yourdomain>" })`), so a new var like `EMAIL_FROM` is a project convention, not an Auth.js one.

**Server-side `signIn()` signature** (`next-auth/index.d.ts:255-263`, `next-auth/lib/actions.js:6-9,42`): `signIn(provider, options, authorizationParams, config)` where `options` can be `{ redirectTo?: string; redirect?: boolean } & Record<string, any>`. The implementation destructures `redirect`/`redirectTo` out and spreads **everything else** (`...rest`) into the POST body as `URLSearchParams({ ...rest, callbackUrl })`. So `signIn("resend", { email, redirectTo })` puts `email` in the POST body exactly as `sendToken` (`@auth/core/lib/actions/signin/send-token.js:9`) expects: `const email = normalizer(body?.email)`.

**`sendToken` flow** (`@auth/core/lib/actions/signin/send-token.js`): normalizes/validates the email (NFKC normalize, lowercase, trim, reject quotes, reject non-`local@domain` shape — throws a descriptive `Error` on bad input, which surfaces as `EmailSignInError`/`AccessDenied` depending on where it fails), calls `adapter.getUserByEmail(email)` (falls back to a throwaway `{id: randomUUID(), email, emailVerified: null}` user object for `callbacks.signIn`), runs the `signIn` callback (can reject → `AccessDenied`), generates a `token` (`provider.generateVerificationToken?.() ?? randomString(32)`), builds the verification URL as:
```
${basePath}/callback/resend?${new URLSearchParams({ callbackUrl, token, email })}
```
(basePath defaults to `/api/auth` for `next-auth`, so **`/api/auth/callback/resend?token=...&email=...&callbackUrl=...`**), calls `provider.sendVerificationRequest(...)` and `adapter.createVerificationToken({ identifier: email, token: await createHash(token+secret), expires })` in parallel, then redirects to `${basePath}/verify-request?provider=resend&type=email`.

**Callback flow for `type: "email"`** (`@auth/core/lib/actions/callback/index.js:131-226`): requires `query.token` (throws a `Configuration`-kind error if absent — **note**: this is the generic `Configuration` error, which this project's `messageForAuthError` already maps to a dedicated "Sign-in isn't configured" message — a slight mismatch worth flagging to `sdd-propose`, since a missing/stripped token is a user-facing link problem, not a server misconfiguration). Calls `adapter.useVerificationToken({ identifier: query.email, token: hash(query.token+secret) })`; if missing/expired/mismatched → throws `Verification` (kind defaults to `"error"` → routed to `pages.error`). Otherwise looks up/creates the user via `adapter.getUserByEmail`, runs `handleLoginOrRegister`, builds the JWT via `callbacks.jwt({ token: defaultToken, user, account, isNewUser, trigger })`, sets the session cookie, fires `events.signIn`, and redirects to `pages.newUser` (if `isNewUser` and configured) else `callbackUrl`.

**`handleLoginOrRegister`** (`@auth/core/lib/actions/callback/handle-login.js:15-89` for the `account.type === "email"` branch): destructures `const { createUser, updateUser, getUser, getUserByAccount, getUserByEmail, linkAccount, createSession, getSessionAndUser, deleteSession } = adapter` **unconditionally** (no per-method guards) — so even though `assertConfig` (below) only *statically* requires 3 methods, the email sign-in code path will throw a runtime `TypeError` the first time it is actually exercised if `createUser`/`updateUser`/`getUser` are missing from the adapter object. Exact logic: if there is an existing `sessionToken` cookie, decode it and `getUser(session.sub)` (JWT strategy: wrapped in try/catch, so a decode failure is swallowed, but a *missing* `getUser` method is a hard `TypeError`, not caught). Then: `getUserByEmail(profile.email)` — if found, `updateUser({ id, emailVerified: new Date() })`; else `createUser({ ...profile, emailVerified: new Date() })` and `isNewUser = true`. `createSession`/`getSessionAndUser`/`deleteSession` are only reached when `sessionStrategy !== "jwt"`, so **not required** for this project's JWT-only setup.

**`assertConfig`** (`@auth/core/lib/utils/assert.js:18-22,128-161`): the *only* methods it statically enforces for an email provider (`emailMethods`) are `createVerificationToken`, `useVerificationToken`, `getUserByEmail`. If the adapter is missing any `requiredMethods`, `Auth()` returns a `MissingAdapterMethods` config error **before any request-specific handling** — and critically, per `@auth/core/index.js:72-107`, a config error on a non-GET/non-html-page action (the `signin` POST that `signIn("resend", ...)` makes) returns a bare `500 JSON { message: "There was a problem with the server configuration..." }`, **not** a redirect to `/login?error=...`. So a correctly-detected-at-build-time-missing adapter method surfaces as an opaque 500 to the Server Function, not the styled error page — the custom adapter's method set must be verified against the *full* runtime requirement (6 methods: `createVerificationToken`, `useVerificationToken`, `getUserByEmail`, `createUser`, `updateUser`, `getUser`), not just the 3 `assertConfig` checks.

**Error → page routing** (`@auth/core/errors.js`, `@auth/core/index.js:120-137`): `AuthError.kind` defaults to `"error"` unless the class extends `SignInError` (kind `"signIn"`). `EmailSignInError extends SignInError` → kind `"signIn"` → routed to `pages.signIn` (`"/login"`) with `?error=EmailSignInError`. `Verification extends AuthError` directly → kind `"error"` (default) → routed to `pages.error` (also `"/login"` in this config) with `?error=Verification`. Both land on `/login` today because `pages.signIn === pages.error === "/login"`, but `messageForAuthError` (`src/app/login/auth-error.ts`) does **not** currently have cases for `"EmailSignInError"` or `"Verification"` — both would silently fall into the `GENERIC` "We couldn't sign you in... Discord didn't complete the sign-in" copy, which explicitly says "Discord" and would be wrong/confusing for an email flow. This file needs new cases and copy, not just a wording tweak.

**`verifyRequest` page**: `pages.verifyRequest` (not currently set) controls the "check your inbox" redirect target; `@auth/core/lib/pages/index.js:107-112` redirects to `${pages.verifyRequest}${url.search}` if set, else renders Auth.js's own unstyled built-in page at the default `/api/auth/verify-request`. This project's existing pattern (`pages: { signIn: "/login", error: "/login" }`) implies adding `verifyRequest: "/login"` (reusing `LoginPanel` with a new third state) or a dedicated `/login/check-email`-style route — a decision for `sdd-propose`.

### Adapter options compared

**Minimum Adapter methods Auth.js actually calls** for this project's JWT-strategy email flow (derived from source above, union of `assertConfig`'s static check and `handleLoginOrRegister`'s unconditional destructuring): `createVerificationToken`, `useVerificationToken`, `getUserByEmail`, `createUser`, `updateUser`, `getUser`. (`linkAccount`/`getUserByAccount`/`createSession`/`getSessionAndUser`/`updateSession`/`deleteSession` are either OAuth/webauthn-only or database-session-only — not reached by this project's JWT + email-only path, *provided Discord stays removed*; if Discord and email coexist as separate providers under one adapter, the OAuth branch of `handleLoginOrRegister` also needs `getUserByAccount`/`linkAccount`, but the proposal removes Discord entirely so this does not apply.)

**Option A — `@auth/d1-adapter` (npm `1.11.3`, NOT installed)**: confirmed via npm/docs (WebSearch — package page + authjs.dev/getting-started/adapters/d1) that it creates its **own** 4 fixed tables — `accounts`, `sessions`, `users`, `verification_tokens` — with **no configurable prefix**, via an `up(env.db)` migration helper. This **collides by name** with this project's existing hand-rolled `users` table (different columns: `id, discord_id, display_name, avatar_url, created_at` vs. Auth.js's `id, name, email, emailVerified, image`). Using this adapter as-is would require either renaming the project's `users` table or forking the adapter's bundled migration SQL to merge columns — effectively becoming a custom adapter anyway, with less control over the hexagonal `UserRepository` port boundary this codebase otherwise maintains strictly (every other feature routes DB access through `src/domain/ports/*` + `src/adapters/db/*`).

**Option B — minimal custom `Adapter` over existing hexagonal ports**: implement a plain object satisfying the `Adapter` interface (`@auth/core/adapters.d.ts:268-397`) by composing: (1) an extended `UserRepository` with `getUserByEmail`/`createUser`/`updateUser`/`getUser` methods that map to the existing `users` table (now keyed by `email` instead of/alongside `discord_id`), and (2) a new small `VerificationTokenRepository` port + D1-backed adapter for `createVerificationToken`/`useVerificationToken`, backed by a new migration adding a `verification_tokens` table (`identifier`, `token` (hashed), `expires`) — Auth.js's own documented minimal shape (`@auth/core/adapters.d.ts:224-241`). This keeps every DB access behind this project's existing port/adapter convention and requires no table-name renames.

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| **A. `@auth/d1-adapter`** | Zero custom adapter code; "official" package | Forces its own `users`/`accounts`/`sessions`/`verification_tokens` schema with no prefix — collides with existing `users` table name; breaks the hexagonal port convention (DB access would bypass `UserRepository`); pulls in session/account machinery this project does not use (JWT-only, single provider) | Medium (schema surgery + migration risk) despite "zero code" |
| **B. Minimal custom Adapter over hexagonal ports** | No table-name collision; keeps every DB read/write behind `UserRepository`/new `VerificationTokenRepository` ports, matching this codebase's established pattern (see `src/adapters/db/user-repository.ts`); only 2 new tables/columns, both additive migrations | More adapter code to write and keep in sync with Auth.js's `Adapter` interface (6 methods minimum, verified above) | Low–Medium |

### Risks

- **Runtime-only adapter requirement gap**: `assertConfig` only checks 3 of the 6 methods `handleLoginOrRegister` actually calls for email sign-in (`createUser`/`updateUser`/`getUser` are unchecked at config time). A custom adapter missing one of these fails with an opaque `TypeError` only when a real sign-in is attempted, not at boot.
- **Misconfigured-adapter error surfaces as bare 500 JSON, not the styled `/login` page**: `MissingAdapter`/`MissingAdapterMethods` on the `signin` POST action return `Response.json({message: "..."}, {status: 500})` per `@auth/core/index.js:85-89`, bypassing `pages.error` entirely (that branch only redirects for GET html-page actions).
- **`messageForAuthError` has no cases for `"EmailSignInError"` or `"Verification"`** — both currently fall through to Discord-specific `GENERIC` copy ("Discord didn't complete the sign-in"), which is wrong for this flow and must be added.
- **`Configuration` error code is reused for two different situations**: a genuinely missing adapter method *and* a magic link opened with the `token` query param stripped/malformed (`@auth/core/lib/actions/callback/index.js:134-138`) both throw a `Configuration`-kind error. This project's existing `Configuration` copy ("Sign-in isn't configured... This is on us, not on you") is accurate for the first case but misleading for the second (a user-side stale/mangled link).
- **No rate limiting exists anywhere in this codebase** (`rg` found no `src/middleware.ts`). The new `/api/auth/signin/resend` POST endpoint is unauthenticated by nature (that's the point of magic-link) and could be hit repeatedly to spam arbitrary inboxes or exhaust the Resend quota/budget; there is no existing pattern (Cloudflare rate-limiting rule, D1-backed counter, Turnstile) to copy from.
- **Token TTL**: Resend provider defaults `maxAge: 24 * 60 * 60` (24h) — likely too long for a security-sensitive magic link; needs an explicit decision (Auth.js email links are commonly set to 10–15 min).
- **`safeReturnPath`/open-redirect reuse**: `signIn("resend", { email, redirectTo })`'s `redirectTo` flows into `callbackUrl` exactly like the Discord flow today, so the existing `safeReturnPath` validation in `actions.ts` still applies unchanged — low risk, but must be re-wired into whatever new Server Function replaces `signInWithDiscordAction`.
- **`.dev.vars` typing**: `cloudflare-env.d.ts` is generated by `wrangler types` (`pnpm cf-typegen`) from `wrangler.jsonc` vars/bindings, not from `.dev.vars` keys directly — adding `AUTH_RESEND_KEY`/`EMAIL_FROM` to `.dev.vars.example` does not by itself add typed fields; whether that matters depends on whether any code reads them via `env.AUTH_RESEND_KEY` (Cloudflare binding) vs. `process.env.AUTH_RESEND_KEY` (the existing Discord pattern, which needs no typegen change).
- **E2E seed/fixture coupling to `discord_id`**: `e2e/fixtures/seed.sql` and `e2e/fixtures/session.ts`'s `SessionUser` type (`{id, discordId, name}`) both assume a `discord_id` column exists and is populated — if the schema migration drops/renames that column, both must be updated in the same change, and the e2e strategy for a magic-link flow without a real inbox needs its own answer (likely: keep minting the JWT cookie directly, as today, since the e2e fixture never actually drives `signIn()`).
- **Display-name source**: the mockup's "05 Cuenta nueva" state is built around an *already-linked Riot account* + a display-name `Input`, not a bare post-email-signup step — reusing it for email sign-up needs the "Connected" Riot block removed/decided separately from reusing the `Input`.

### Open Questions (for sdd-propose)

1. Does the proposal keep `discordId` as a nullable legacy column (future-proofing if Discord ever returns) or drop it outright in the migration, given zero production rows exist?
2. Token TTL for the magic link — reuse Resend's 24h default or shorten it (and does a one-time-code UI need a different TTL/UX than a link)?
3. Where does `pages.verifyRequest` point — a third `LoginPanel` state at `/login`, or a dedicated route?
4. Is the "05 Cuenta nueva" display-name step adopted for first email sign-in (local-part-of-email default, user can edit) or skipped (derive `displayName` straight from the email local part, no extra step)?
5. What throttling mechanism (if any) protects the unauthenticated send-magic-link endpoint from abuse, given no existing rate-limiting pattern in this codebase?
6. Does `messageForAuthError` get new cases for `EmailSignInError`/`Verification`, and does the generic `Configuration` case get split to distinguish "server misconfigured" from "stale/malformed link"?

### Recommendation

Option B (minimal custom Adapter over the existing hexagonal `UserRepository`/new `VerificationTokenRepository` ports) over Option A (`@auth/d1-adapter`). The d1-adapter's fixed, unprefixed `users`/`accounts`/`sessions`/`verification_tokens` schema directly collides with this project's existing `users` table and would force either a rename or a schema fork, while also pulling in session/account machinery (`accounts`, `sessions` tables) this JWT-only, single-provider app does not need. A custom adapter is more code but stays inside the project's established port/adapter convention, needs only two small additive migrations (a `verification_tokens` table + email column(s) on `users`), and gives full control over exactly which 6 methods are implemented (verified from source: `createVerificationToken`, `useVerificationToken`, `getUserByEmail`, `createUser`, `updateUser`, `getUser`).
