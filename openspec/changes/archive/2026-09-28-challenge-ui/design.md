# Design: Challenge UI (T12) on the Become a Legend design system

Change: `challenge-ui` · Store: hybrid (this file + Engram topic `sdd/challenge-ui/design`, project `challenges2026`) · Inputs: `proposal.md` (A1–A14, S0–S7, R1–R12), `specs/{design-system,challenge-authoring,challenge-discovery,challenge-participation,challenge-view}/spec.md` (34 requirements), `research.md`, `exploration.md`.

**In one line:** vendor the exported tokens behind a Tailwind 4 `@theme inline` mapping, port the primitives as server-renderable TSX, add three additive port methods and four typed-result use cases, then build three routes on the `/account` trio pattern — delivered as eight chained slices, each independently buildable.

---

## Technical Approach

Four layers change, in dependency order, and nothing below the UI is re-architected.

| Layer | What this change does | What it does not do |
|---|---|---|
| CSS / assets | Vendors `design/_ds/.../tokens/*.css` into `src/styles/tokens/`, maps them into Tailwind 4 with `@theme inline`, self-hosts three fonts via `next/font/local`, vendors 14 Lucide glyphs | No CSS-in-JS, no runtime CDN, no theme toggle (A8), no tier tokens |
| Components | Ports 10 core/form primitives plus 3 reduced game components to TSX over Tailwind utilities | Ports nothing that renders coins, tiers, XP, avatars or a destination that does not exist (R8) |
| Domain / ports / adapters | Adds `listPublic`, `listProgressForChallenge`, `findById`; adds `rule-text.ts`, `rule-presets.ts`, `safeParseRules` | No schema change, no migration, no new external service |
| Application / routes | Adds 4 use cases returning `{ kind: ... }` unions and 3 routes on the server-page + `"use server"` actions + one `"use client"` form pattern | Never calls `evaluate` from the UI; never imports `src/adapters` from `src/application` |

The hexagonal rule from `openspec/config.yaml` holds: **`src/application` imports only `src/domain`**. The composition roots are the routes' `page.tsx` and `actions.ts` — the only new files allowed to import `src/adapters/db/*`, exactly as `src/app/account/actions.ts` does today.

## Architecture Decisions

### D1 — Vendor the token CSS files instead of importing `design/` directly

**Choice**: copy `colors.css`, `typography.css`, `spacing.css`, `radius.css`, `elevation.css`, `motion.css`, `base.css` byte-for-byte into `src/styles/tokens/`. Do **not** vendor `fonts.css` (D4) or `tiers.css` (nothing renders tiers).

**Alternatives considered**: (a) `@import "../../design/_ds/…/styles.css"` straight from the export directory; (b) convert the tokens to a TS object and generate CSS.

**Rationale**: `design/` is an *export target* — the owner re-exports from Claude Design and the folder name carries a UUID (`become-a-legend-design-system-cbebf259-…`) that changes with the design system, not with the app. Importing it directly couples the build to a path the design tool owns and ships five `.dc.html` canvases, two JS bundles and a 278-line README into the app's dependency graph. Vendoring byte-identical files keeps a re-export a clean `cp` + `git diff`, which is the property the proposal asked for, while the app owns its own build inputs. (b) loses the "change a token, rebuild, every utility follows" property the design-system spec requires.

### D2 — Map tokens through an owned `--bal-*` indirection file, not name-for-name

**Choice**: add one owned file `src/styles/tokens/app-aliases.css` that re-exposes, under a `--bal-` prefix, every vendored token whose name collides with a Tailwind 4 theme namespace. `@theme inline` then maps `--radius-card: var(--bal-radius-card)`, never `--radius-card: var(--radius-card)`.

**Alternatives considered**: (a) map each token to itself inside `@theme inline`; (b) rename tokens inside the vendored files; (c) give the Tailwind tokens ugly prefixed names (`--radius-bal-card` → `rounded-bal-card`).

**Rationale**: the export's namespace overlaps Tailwind 4's theme namespaces in six places — `--text-*` (Tailwind: font-size), `--font-*`, `--radius-*`, `--shadow-*`, `--tracking-*`, `--ease-*`, `--container-*`. A self-referential `@theme` entry emits a declaration whose value references the same property name; if Tailwind emits it into `:root` after the vendored declaration, the custom property becomes cyclic and therefore guaranteed-invalid, silently blanking the token. The behaviour depends on emission order and on `inline` semantics we would be inferring rather than relying on. (b) makes every design re-export a manual merge instead of an overwrite, defeating D1. (c) produces `rounded-bal-card` / `text-bal-display-1` in every component, which is the cost paid forever to avoid ~25 alias lines paid once. The indirection file is also the single place to re-check after a re-export.

### D3 — Fix the export's one real token collision explicitly

**Discovered defect**: the export declares `--text-body` **twice** — `colors.css` sets it to `var(--ink-100)` (a colour), `typography.css` sets it to `16px` (a font size). `styles.css` imports `typography.css` after `colors.css`, so the size wins, and the export's own `base.css` rule `body{color:var(--text-body)}` resolves to `color: 16px`, an invalid declaration that is dropped — leaving the body text at the UA default (black) on a `#08090A` canvas. Under `[data-theme="light"]` the direction reverses: `--text-body` becomes `var(--ink-900)` and every *font size* bound to it breaks instead.

**Choice**: `app-aliases.css` declares `--bal-text-body-color: var(--ink-100)` (and `var(--ink-900)` under `[data-theme="light"]`) and `--bal-text-body-size: 16px`. `@theme inline` maps `--color-text-body: var(--bal-text-body-color)` and `--text-body: var(--bal-text-body-size)`.

**Alternatives considered**: reorder the imports (breaks the other consumer); patch the vendored `colors.css` (breaks D1); ignore it (ships unreadable body text).

**Rationale**: it is the only genuine collision in the export, and it has to be resolved in a file we own so that a design re-export cannot silently reintroduce it. `--bal-text-body-size: 16px` is the **single hardcoded value** in the whole token pipeline; it is hardcoded because the vendored name is shadowed under `[data-theme="light"]`, so a `var()` reference would resolve to a colour inside a light subtree. It carries a comment saying so and is the first thing to delete if the export ever renames either side.

### D4 — Self-host the three families with `next/font/local`, and skip the exported `fonts.css`

**Choice**: `src/app/fonts.ts` declares Space Grotesk, Instrument Sans and JetBrains Mono with `next/font/local`, latin subset, variable `woff2` where available. An owned `src/styles/tokens/app-fonts.css` binds the design's family tokens to them. The export's `fonts.css` (a `fonts.googleapis.com` `@import`) is never vendored.

**Alternatives considered**: `next/font/google` (still a build-time fetch and a Google-hosted file list); vendoring `fonts.css` and stripping the `@import` (leaves a file the design tool will re-export with the `@import` back in).

**Rationale**: R4 — a runtime CDN request from a Cloudflare Worker is both a latency/availability dependency and a third-party request the shipped privacy policy does not declare. `design-system` spec: "the built worker MUST NOT issue any runtime network request to `fonts.googleapis.com`". Not vendoring `fonts.css` at all means a re-export cannot reintroduce the `@import`, because the app never reads that file.

### D5 — Do not map `--space-*` into Tailwind's spacing namespace

**Choice**: keep Tailwind 4's default `--spacing: 0.25rem` scale. Map only `--container-max` / `--container-prose`. Document the design-to-Tailwind spacing equivalence table.

**Alternatives considered**: `@theme inline { --spacing-6: var(--space-6); … }`.

**Rationale**: the design's scale is 4px-based but **non-linear** — `--space-6` is 20px, `--space-7` is 24px. Mapping it onto Tailwind's numeric names would make `p-6` mean 20px instead of Tailwind's 24px: every numeric spacing utility in the codebase and in every future snippet would silently mean something else. Tailwind's own 4px scale already expresses the design's intent (`px-5` = 20px = `--gutter-mobile`, `lg:px-10` = 40px = `--gutter-desktop`, `p-7` = 28px = the dashboard padding), so the mapping buys nothing and costs a permanent trap.

### D6 — Import the vendored `base.css` into `@layer base`

**Choice**: `@import "../styles/tokens/base.css" layer(base);` — every other token file is imported unlayered.

**Rationale**: unlayered CSS beats *all* layered CSS in the cascade. Imported plainly, the export's `body{background:…;font-family:…}` and `h1,h2,h3,h4{font-family:var(--font-display)}` would defeat every Tailwind utility applied to those elements — `<h2 className="font-body">` would not work and would look like a Tailwind bug. The other files declare custom properties only, where specificity is irrelevant, so they stay unlayered and readable.

### D7 — The `dark:` variant is redefined as a shim in S0 and deleted in S6 (revises R7)

**Evidence**: grep across `src/` shows **no** component uses `bg-background`, `text-foreground`, `font-sans` or `font-mono`. The only consumer of `--background`/`--foreground` is `globals.css` itself. What *is* used, in six files, is **21** `dark:` utilities resolved from `prefers-color-scheme` — measured with `rg -o "dark:" src/`:

| File | `dark:` utilities |
|---|---|
| `src/app/account/page.tsx` | 6 |
| `src/app/account/link-form.tsx` | 5 |
| `src/app/page.tsx` | 4 |
| `src/components/auth-status.tsx` | 3 |
| `src/components/site-footer.tsx` | 2 |
| `src/components/legal-page.tsx` | 1 |
| **Total** | **21** |

They are not all the same shape: 9 `text-black/70 dark:text-white/70`-style text-colour pairs, 9 `border-black/10 dark:border-white/15`-style border pairs, 2 accent pairs in `link-form.tsx` (`dark:text-green-*`, `dark:text-red-*`) and 1 amber pair in `account/page.tsx` — 21 in total. Every one of them inverts on a light-OS profile.

**Choice**: S0 keeps the `--color-background` / `--color-foreground` aliases (cheap, and the proposal committed to them) **and** adds the real shim:

```css
/* S0→S6 shim. The product is dark-only (A8), but six pre-existing files still
   carry `dark:` pairs resolved from prefers-color-scheme. Without this, a
   visitor on a light OS gets `text-black/70` on a #08090A canvas. Deleted in
   S6 once those pairs are on semantic tokens. */
@custom-variant dark (&:where(:root, :root *));
```

**Alternatives considered**: sweep the 21 pairs in S0 (merges S6 into S0 and puts S0 over budget); leave `prefers-color-scheme` alone (ships an unreadable page to every light-OS visitor the moment S0 lands — an S0-only regression the proposal did not catch).

**Rationale**: R7 named the right risk but the wrong mechanism. The token swap does not break those pages through `--background`; it breaks them through the `dark:` variant. One `@custom-variant` line makes every `dark:` utility always apply, which is precisely correct for a dark-only product, and it is deleted in the same slice as the pairs it protects.

### D8 — Primitives are server-renderable: Tailwind variants, not `useState` hover

**Choice**: no primitive in `src/components/ui/` carries `"use client"`. Hover, press, focus and disabled are Tailwind variants (`hover:`, `active:`, `focus-visible:`, `disabled:`), not React state. `Button` exposes no `onClick`; it spreads `ButtonHTMLAttributes` so forms and server actions drive it.

**Alternatives considered**: port the export's `React.useState(hover)` pattern verbatim; mark every primitive `"use client"`.

**Rationale**: the export is a canvas preview, so it simulates CSS with JS. Copying that would force a client boundary onto every page that renders a `Card`, shipping JS for a background colour, on a project whose existing pages ship almost none (`AuthStatus` signs in and out with zero client JS). A directive-free component inherits the boundary of whoever imports it, so the same `Button` works in a server page and inside `create-form.tsx`.

### D9 — `Input`/`Select` are uncontrolled; the server action is the only validator

**Choice**: the ported form primitives keep the export's `label`/`hint`/`error`/`icon`/`suffix` props but drop `value`/`onChange` in favour of native `name`/`defaultValue`, spreading `InputHTMLAttributes`. `error` drives `aria-invalid` and `aria-describedby`.

**Rationale**: every form in this app submits `FormData` to a server action (`/account` already does), and the `challenge-authoring` spec requires validation through `parseRules` server-side with **no parallel UI schema**. Controlled inputs would add state with nothing to do and would tempt a second validation layer. The rule builder is the one place that genuinely needs React state (D13), and it keeps it.

### D10 — Reduced `ChallengeCard` / `PlayerRow` / `StatTile` drop props, not just values

**Choice**: the ported variants have **no prop** for coins, stake, XP, tier, rank, record, avatar, `challenger`/`opponent`, `delta` or `deltaTone`.

| Export props | Ported props |
|---|---|
| `ChallengeCard({ challenger, opponent, game, queue, status, stake, xp, meta, onAccept, onDecline, onClick })` | `ChallengeCard({ href, title, state, ruleText, endsAt })` |
| `PlayerRow({ name, handle, tier, rank, record, right, online, onClick })` | `PlayerRow({ name, meta, right })` |
| `StatTile({ label, value, delta, deltaTone, icon })` | `StatTile({ label, value, hint })` |

**Rationale**: R8 — a prop that accepts data the backend cannot produce gets passed `0` or `undefined` and renders a zero balance or an empty tier, which reads as a broken feature rather than an absent one. Removing the prop makes the absence a compile-time fact; a future coin feature adds a prop back, visibly, in a PR that also adds the data. `status` is also re-domained: the export's `pendiente|vivo|ganado|perdido` becomes the spec's `upcoming|live|ended`, because the app's state is derived from a window, not from a duel outcome.

### D11 — Rule-to-words lives in the domain (`src/domain/rule-text.ts`)

**Choice**: `ruleToSentence(rule: Rule): string` and `rulesToSentences(rules: Rule[]): string[]`, pure, no React, with `ROLE_LABELS` and `QUEUE_LABELS` added to `src/domain/match.ts` next to `ROLES`/`QUEUES`.

**Alternatives considered**: a helper inside the view component; a `formatRule` in `src/lib/`.

**Rationale**: three separate consumers need the identical sentence — the review step of the create wizard (R2's typo mitigation: "Win 3 games as *Ahri*" makes a misspelling visible before submit), the browse card, and the view page — and the `challenge-view` spec states the output contract ("Win 3 games as Ahri", "Play 20 games") as a requirement with scenarios. A requirement with scenarios belongs where Vitest can run it under `environment: "node"` with no DOM, which is `src/domain`. The precedent is already there: `PLATFORM_LABELS` lives in `src/domain/riot-id.ts`, not in the form that renders it.

Sentence template, deterministic:

```
{Win|Play} {target} {queueWord?} {game|games}{ as {champion}}{ in {roleLabel}}
```

`Win` when a `won` criterion is present, else `Play`; `game` when `target === 1`. Examples: `Win 3 games as Ahri` · `Play 20 games` · `Win 10 ranked solo games in Jungle` · `Win 1 game`.

### D12 — Presets are domain data (`src/domain/rule-presets.ts`), not form state

**Choice**: `RULE_PRESETS` is an exported array of `{ id, label, description, build(args): Rule }`, tested by asserting each `build(...)` output survives `parseRules`.

**Rationale**: A11 says presets are convenience that pre-fills an editable rule and never a separate stored shape. Expressing them as functions that return a `Rule` makes that literally true and testable; expressing them as JSX defaults inside the wizard would let a preset drift into a shape `parseRules` rejects, discovered only by a user.

### D13 — One hidden `rulesJson` field, `parseRules` as the only schema

**Choice**: the rule builder holds its draft in `useState<Rule[]>` and renders `<input type="hidden" name="rulesJson" value={JSON.stringify(rules)} />`. The server action calls `safeParseRules(formData.get("rulesJson"))`.

**Alternatives considered**: indexed field names (`rules[0].criteria[1].champion`) reassembled server-side; a zod schema mirrored in the client.

**Rationale**: the rules are a nested variable-length structure; indexed names would need a parser on the server that is itself a second schema — the exact duplication the `challenge-authoring` spec forbids. One JSON string means the form and the database are validated by the same function `createChallengeRepository` already uses, so they cannot disagree.

### D14 — `safeParseRules` in the domain, so the application layer never imports zod

**Choice**: add to `src/domain/rule-codec.ts`:

```ts
export type ParsedRules =
  | { ok: true; rules: Rule[] }
  | { ok: false; reason: "not_json" | "invalid"; ruleIndex: number | null; field: string | null };

export function safeParseRules(json: string): ParsedRules;
```

It wraps `JSON.parse` + `rulesSchema.safeParse` and translates `issues[0].path` (`[2, "target"]`) into `{ ruleIndex: 2, field: "target" }`.

**Alternatives considered**: catch `ZodError` in `createChallenge`.

**Rationale**: `challenge-authoring` requires the error to *name the offending rule*. Deriving that from a zod issue path is schema knowledge, and schema knowledge lives with the schema. It also keeps zod out of `src/application`, matching how `linkRiotAccount` consumes `parseRiotId` rather than a schema. `parseRules`/`serialiseRules` keep throwing and keep their existing callers.

### D15 — Browse cards carry no participant count

**Choice**: `ChallengeSummary` is `{ id, title, startsAt, endsAt, state, ruleText }`. No count.

**Alternatives considered**: a `countParticipants` port method or a `listParticipants` call per listed challenge.

**Rationale**: no `challenge-discovery` requirement asks for it, and either implementation is a new port method or an N+1 on the one page that is public and uncached. The card's job is "what is this and how long is left".

### D16 — E2E signs in by minting the Auth.js cookie; nothing test-only ships

**Choice**: Playwright's fixture calls `encode` from `next-auth/jwt` and sets the cookie directly. No provider, no route, no env flag in production code (A14).

**Alternatives considered**: a gated Credentials provider in `auth.ts`; a `/api/test/sign-in` route.

**Rationale**: this codebase is under Riot production-key review; a permanent authentication bypass surface, however gated, is a reviewable security fact forever, while a fixture is deleted with the `e2e/` folder. The coupling risk (R9) is bounded because `next-auth` is pinned to the exact `5.0.0-beta.32`, not a range.

Two internals the fixture depends on, verified in `node_modules/@auth/core@0.41.3` source rather than assumed:

| Internal | Value | Source |
|---|---|---|
| Cookie name over plain http | `authjs.session-token` (the `__Secure-` prefix is added only when `useSecureCookies`) | `src/lib/utils/cookie.ts` → `defaultCookies()` |
| `encode` params | `{ token, secret, salt, maxAge }` — **`salt` is required** and the key is derived from it | `src/jwt.ts` → `encode()` |
| `salt` value | the cookie name: `getToken` defaults `salt = cookieName` | `src/jwt.ts` → `getToken()` |

So the fixture must pass `salt: "authjs.session-token"` or the app will fail to decrypt a token it just minted. The token payload needs `userId` (read by `sessionFromToken` in `src/auth/callbacks.ts`), plus `sub` and `name` for display.

### D17 — Seed local D1 through `wrangler d1 execute --local`, from `globalSetup`

**Choice**: `e2e/global-setup.ts` runs `wrangler d1 execute DB --local --file e2e/fixtures/seed.sql` with `execFileSync` (argv array, no shell string), then reads one row back to prove it applied.

**Alternatives considered**: open the miniflare SQLite file directly with `@libsql/client` (already a devDependency).

**Rationale**: the local D1 file lives at a miniflare-owned path (`.wrangler/state/v3/d1/miniflare-D1DatabaseObject/<hash>.sqlite`) that is an implementation detail of the version of wrangler installed. `wrangler` already owns that mapping and is already a devDependency. The read-back matters because a seed that silently did nothing produces a confusing test failure three steps later.

### D18 — The join redirect carries a machine-readable reason

**Choice**: the join action redirects to `/account?reason=sign-in-to-join` or `/account?reason=link-account-to-join`; `/account/page.tsx` reads `PageProps<'/account'>`'s `searchParams`, maps the closed union to copy, and renders a banner.

**Alternatives considered**: a cookie-based flash message; redirecting without a reason.

**Rationale**: `challenge-participation` requires the user to be "redirected to `/account` **with the reason stated**". A query parameter is stateless, survives a full page load with JS off, and is directly assertable in the e2e spec. The union is closed so an unrecognised value renders nothing rather than reflecting arbitrary text.

### Adapter implementation shape

| Method | Query | Index used |
|---|---|---|
| `listPublic` | `select * from challenges where visibility = 'public' and starts_at <= ? and ends_at >= ? order by ends_at asc, id asc limit ?` — Drizzle `and(eq(visibility,"public"), lte(startsAt, now), gte(endsAt, now))`, `.orderBy(asc(endsAt), asc(id))`, `.limit(limit)`; rows through the existing `toStoredChallenge` | `challenges_window_idx (ends_at, starts_at)` |
| `listProgressForChallenge` | `select riot_account_id, rule_index, current, target, completed_at from progress where challenge_id = ? order by riot_account_id asc, rule_index asc`, grouped in the adapter into `ParticipantProgress[]` preserving `rule_index` order and mapping `completed = completedAt !== null` (identical to `findProgress`) | `progress` PK `(challenge_id, riot_account_id, rule_index)` |
| `findById` | `select * from riot_accounts where id = ? limit 1`, through the existing `toRiotAccount` (keeping its platform/region corruption guards) | primary key |

Both bounds of `listPublic` are **inclusive**, matching `listActiveAt` and `evaluate` — if storage disagreed, a challenge would vanish from the browse list on the day it ends while still being polled.

## 7. Use cases (S3)

All in `src/application/`, factory + typed result, no thrown domain errors, no `src/adapters` import.

```ts
// create-challenge.ts
export type CreateChallengeInput = {
  ownerId: string;
  title: string;
  startsAt: string;            // raw <input type="datetime-local"> value
  endsAt: string;
  visibility: string;          // raw form value
  rulesJson: string;           // the one hidden field (D13)
  joinAsRiotAccountId: string | null;
};

export type CreateChallengeResult =
  | { kind: "created"; id: string }
  | { kind: "invalid_title" }
  | { kind: "invalid_window"; reason: "unparseable" | "end_not_after_start" }
  | { kind: "invalid_visibility" }
  | { kind: "invalid_rules"; ruleIndex: number | null; field: string | null }
  | { kind: "too_many_rules"; limit: 5 }
  | { kind: "too_many_criteria"; ruleIndex: number; limit: 4 }
  | { kind: "riot_account_not_owned" };

export function createChallenge(deps: {
  challenges: ChallengeRepository;
  riotAccounts: RiotAccountRepository;
  newId: () => string;
}): (input: CreateChallengeInput) => Promise<CreateChallengeResult>;
```

**Validation order** — cheapest and most user-visible first, storage last:

1. `title.trim()` non-empty → else `invalid_title`.
2. `new Date(startsAt/endsAt)` parse → `NaN` → `invalid_window: "unparseable"`.
3. `endsAt > startsAt` → else `invalid_window: "end_not_after_start"`.
4. `visibility` ∈ `{public, unlisted}` → else `invalid_visibility`.
5. `safeParseRules(rulesJson)` → else `invalid_rules` carrying `ruleIndex`/`field` (D14).
6. Caps: `rules.length <= 5`, each `criteria.length <= 4`. **Re-checked server-side** even though the builder enforces them, because a Server Function is reachable by direct POST (Next docs) and `rule-codec.ts` sets no upper bound.
7. If `joinAsRiotAccountId` is non-null: `riotAccounts.findById` → null or `userId !== ownerId` → `riot_account_not_owned`.
8. `id = newId()`; `challenges.create({...})`; if joining, `challenges.join(id, accountId)`; return `created`.

`newId` is injected (defaulting to `crypto.randomUUID` at the composition root) for the same reason `linkRiotAccount` injects `matchProviderFor`: a test must be able to assert the stored id. Create-then-join is **not** transactional across this port — if `join` rejects, the challenge exists with zero participants, which the poller already tolerates (it iterates participants) and the creator can fix by joining from the challenge page. Documented rather than papered over with a compensating delete.

```ts
// join-challenge.ts
export type JoinChallengeInput = { userId: string; challengeId: string; riotAccountId: string };

export type JoinChallengeResult =
  | { kind: "joined" }
  | { kind: "already_joined" }
  | { kind: "challenge_not_found" }
  | { kind: "challenge_ended" }
  | { kind: "riot_account_not_owned" };

export function joinChallenge(deps: {
  challenges: ChallengeRepository;
  riotAccounts: RiotAccountRepository;
  now: () => Date;
}): (input: JoinChallengeInput) => Promise<JoinChallengeResult>;
```

Order: `findById` challenge → `challenge_not_found`; `now() > endsAt` → `challenge_ended` (upcoming and live both allowed — owner-approved inference); `riotAccounts.findById` → null or foreign `userId` → `riot_account_not_owned`; `listParticipants` contains the id → `already_joined`; else `join`. The ownership check uses `findById` rather than `listByUser` because it is one row instead of a list, and the method exists now. The pre-check exists only to *report* `already_joined`; correctness is the adapter's `onConflictDoNothing`, so a race reports `joined` twice and still stores one row — which satisfies "exactly one participant row" and is the only part of the spec a race can affect.

// get-challenge-view.ts

export type ParticipantView = {

Flow: `findById` → `not_found`; then `listParticipants` and `listProgressForChallenge` concurrently; for each participant id, `riotAccounts.findById` then `polling.getState(puuid)` (per-participant calls accepted at friends scale, per the proposal). State derives from `now()` against the window, never from a stored column. Progress is zero-filled to `challenge.rules.length` so a joined-but-unpolled participant renders `0 / N` instead of disappearing. Participants are sorted by lowercased `displayName` ascending in the use case — `listParticipants` specifies no order, and the view and its e2e assertions need a deterministic one; changing that existing method's contract was rejected as a wider blast radius than a sort.

| `preset` | `RULE_PRESETS` as selectable `Card`s + "Start from scratch" | one rule appended to the draft |
| `rules` | the rule builder: 1–5 rules, each target + 0–4 criteria chips (`Tag`), add/remove controls disabled at the caps | a valid-shaped draft |
| `details` | title, `startsAt`, `endsAt` (`datetime-local`), visibility `Radio` pair, self-join `Checkbox` + account `Select` when >1 linked account | — |
| `review` | every rule restated by `ruleToSentence` (R2's typo mitigation), the window, visibility, self-join; the only `type="submit"` button | POST |

**One form, all steps mounted.** A single `<form action={formAction}>` wraps every step; inactive steps are hidden with the `hidden` attribute so `FormData` always carries every field and Back never loses input. No `required` attributes are used — native validation cannot focus a hidden field, and the server action is the validator anyway (D9, `challenge-authoring` spec).

**Self-join control** (A5 + spec): unavailable with an explanation when `accounts.length === 0`; a bare `Checkbox` plus a hidden `riotAccountId` when exactly 1; a `Checkbox` plus a `Select` when >1.

```ts
export type JoinChallengeActionState = JoinChallengeResult | { kind: "unauthenticated" };

export async function joinChallengeAction(prev, formData): Promise<JoinChallengeActionState> {
  const session = await auth();
  if (!session?.user?.id) redirect("/account?reason=sign-in-to-join");     // D18

  const db = await getAppDb();
  const riotAccounts = createRiotAccountRepository(db);
  const accounts = await riotAccounts.listByUser(session.user.id);
  if (accounts.length === 0) redirect("/account?reason=link-account-to-join");

  const challengeId = String(formData.get("challengeId") ?? "");
  const riotAccountId = String(formData.get("riotAccountId") ?? accounts[0]!.id);

  const result = await joinChallenge({ challenges: createChallengeRepository(db), riotAccounts, now: () => new Date() })(
    { userId: session.user.id, challengeId, riotAccountId },
  );

  if (result.kind === "joined") revalidatePath(`/challenges/${challengeId}`);  // literal path, no type
  return result;
}
```
