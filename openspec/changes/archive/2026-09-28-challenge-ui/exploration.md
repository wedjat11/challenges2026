# Exploration: T12 Challenge UI (create, browse, join, view)

Change: `challenge-ui` · Engram mirror: topic `sdd/challenge-ui/explore` (project `challenges2026`, obs #46) · Written 2026-09-18 by `sdd-explore`; persisted to OpenSpec by the orchestrator because the exploration agent has no file-write tool.

## Current State

Hexagonal layers already exist for everything the UI needs to read/write except the UI itself:

- Domain: `Rule`/`Criterion` (`src/domain/rule.ts`), zod validation of `Rule[]` to/from JSON (`src/domain/rule-codec.ts`, exports `parseRules`/`serialiseRules`, both throw on invalid input — no separately exported schema), `evaluate`/`ChallengeProgress`/`RuleProgress` (`src/domain/progress.ts` — pure, UI must never call this, only read stored results), `Role`/`Queue` enums (`src/domain/match.ts`), `Platform`/`Region`/`PLATFORM_LABELS` (`src/domain/riot-id.ts`).
- Ports: `ChallengeRepository` (create/findById/join/listParticipants/saveProgress/findProgress/listActiveAt/listActiveForAccount), `RiotAccountRepository` (link/listByUser/findByPuuid/unlink — no `findById`), `PollingRepository` (listDue/getState/saveState/cacheMatches/listCached — separate port from `ChallengeRepository` by design, per T11).
- Adapters: `createChallengeRepository` (Drizzle/D1, tested against in-memory SQLite) implements all of the above except listing by visibility or batch progress.
- Schema (`src/db/schema.ts`): `challenges` (id, ownerId, game, title, rulesJson, startsAt, endsAt, visibility public|unlisted, createdAt), `participants` (challengeId+riotAccountId PK), `progress` (challengeId+riotAccountId+ruleIndex PK, current, target, completedAt, updatedAt), `pollState` (puuid+game PK, lastPolledAt, ...).
- UI pattern to reuse (`src/app/account/`): `page.tsx` is an async server component calling `auth()`, building `getAppDb()`-backed repositories, rendering server data plus a `"use client"` form; `actions.ts` holds `"use server"` functions built per-call (DB needs request-scoped Cloudflare context); `link-form.tsx` uses `useActionState` with a typed action-result union and a `messageFor()` switch — no form library in deps, plain React state.
- Auth: `src/auth.ts` (Auth.js, Discord provider, JWT session strategy, no adapter, lazy config), `AuthStatus` server component (sign-in/out via server actions, `Link` to `/account`).
- No `openspec/` directory existed before this exploration (prior SDD state was Engram-only per `sdd-init` obs #39); no Playwright dependency, config, or CI workflow exists anywhere in the repo.

## Answers to the exploration questions

**1. Routes, server/client split, rule-builder pattern.**
Recommended routes: `/challenges/new` (create), `/challenges` (public browse list), `/challenges/[id]` (view + join), following Next 16's `PageProps<'/challenges/[id]'>`/`LayoutProps` generated-type convention already used in `layout.tsx` (confirmed against `node_modules/next/dist/docs/01-app/01-getting-started/03-layouts-and-pages.md`: `params` is a `Promise`, resolved with the global `PageProps<'/route'>` helper generated by `next typegen`/`next dev`/`next build`). No separate join route needed — join is a form/button on the view page, mirroring the account page's inline unlink form. Each route follows the account trio: async server `page.tsx` (session + data fetch) + `"use server"` `actions.ts` + one `"use client"` component using `useActionState`. The rule builder (variable-length list of rules, each with a variable-length list of criteria) is the one genuinely new UI pattern — no existing component manages nested variable-length form state. Recommended approach: keep the rule-builder's live editing state in plain `useState` inside the client component (add/remove rule, add/remove criterion, per-criterion kind switch), and on submit serialize the whole draft to one JSON string in a hidden input; the server action re-validates by calling `parseRules(formData.get("rulesJson"))` — reusing `rule-codec.ts` exactly as `createChallengeRepository` does, with zero new validation logic duplicated.

**2. Missing application layer and repository methods.**
Missing use cases (none exist yet): `createChallenge` (validate title, rules via `parseRules`/`serialiseRules`, `endsAt > startsAt`, visibility enum, generate id, call `create`), `joinChallenge` (must resolve which of the signed-in user's linked Riot accounts to join with — `ChallengeRepository.join` already takes a single `riotAccountId`, so the use case must verify that account is owned by `session.user.id`, e.g. via `RiotAccountRepository.listByUser` — no existing method fetches one account by id), `getChallengeView` (challenge + participants + progress + last-polled-at, composing `ChallengeRepository`, `RiotAccountRepository`, and `PollingRepository`), `listPublicChallenges` (nothing lists by visibility today).
Missing repository methods: `ChallengeRepository.listPublic(...)` (browse page — no existing query filters on `visibility`); a batch progress read across all participants (`findProgress` is per-participant only — looping it per view is N+1 but tolerable at small "friends" scale; a `listProgressForChallenge(challengeId)` batch method is a cheap, cleaner alternative — one query, ties naturally to `listParticipants`); `RiotAccountRepository.findById(id)` (needed to turn a participant's stored `riotAccountId` into a display name (`gameName#tagLine`) and a `puuid` for the poll-state lookup — nothing today resolves a bare id).

**3. Rule-builder UX constraints.**
`Rule = { target, criteria[] }`; empty `criteria` means "play N games" (already how `qualifies`/`evaluate` treat it); `rulesSchema` in `rule-codec.ts` requires `min(1)` rules and each `target` to be a positive int, but places no upper bound on rule or criteria count — the UI, not the domain, must decide any sane cap. Champion criterion validation is `z.string().trim().min(1)` — free text, compared case-insensitively at evaluation time (`sameChampion`) — there is no champion allow-list anywhere in the codebase today, not even in the Riot adapter's match mapper. Two real options: (a) plain free-text input, zero cost, exactly matches existing validation, but a typo silently makes a rule unwinnable until someone notices; (b) fetch Riot's Data Dragon champion list (free, unauthenticated, no API key or rate-limit spend, ~170 names, changes only per patch) to back a `<datalist>`/autocomplete — low effort, catches typos at creation time instead of at evaluation time weeks later. Not required for v1 correctness; flagged as an open product/scope decision (see Q7).

**4. Sharing.**
`visibility: "public" | "unlisted"` already exists on `challenges`; recommend one URL shape for both, `/challenges/[id]`, with `id` presumably a `crypto.randomUUID()` generated by `createChallenge` — unlisted security is UUID opacity, no separate secret-token column exists or is needed given the low sensitivity of "a game goal." An unauthenticated visitor should be able to read a challenge's progress (the acceptance criterion says "a second user opens that URL... and both see progress update automatically," which implies the view must work pre-join, and pre-sign-in for read purposes); only the join action needs to gate on `auth()`, matching the account page's "sign in to do X" fallback pattern.

**5. Progress display and "last updated."**
The UI must only read stored `progress` rows via `findProgress`/the new batch method — never call `evaluate` itself (that stays `pollPlayer`'s job per T11's hexagonal split). "Last updated" has no per-challenge/per-rule timestamp exposed by the domain today: `progress.updatedAt` exists as a DB column but `RuleProgress` (the domain type `findProgress` returns) strips it to `{ current, target, completed }` only. The only currently-surfaced signal is `poll_state.last_polled_at`, one value per `puuid` (not per challenge), reached via `PollingRepository.getState(puuid)` — which needs the participant's `puuid`, i.e. the same `RiotAccountRepository.findById` gap from Q2. Recommend reusing `last_polled_at` (zero domain changes) over extending `RuleProgress` with its own timestamp (an additive but real domain/port change) for v1.

**6. E2E.**
Target `next dev`, not `wrangler dev`: `src/lib/db.ts`'s own comment confirms `getCloudflareContext({ async: true })` "works under both `wrangler dev` and plain `next dev`, because `next.config.ts` calls `initOpenNextCloudflareForDev()`" — so Playwright's `webServer` can drive the much faster `next dev` against the same local D1 binding `wrangler.jsonc` already defines, with no worker-bundling step. No CI workflow exists in this repo, so e2e is a local-only run until CI is explicitly requested — not a v1 blocker. Auth-without-Discord options, ranked: (1) session-cookie injection — Playwright mints/sets the Auth.js JWT session cookie directly (via `next-auth/jwt`'s encode, using `AUTH_SECRET`) with zero production code changes, all risk contained in the test harness; version-coupled to next-auth internals, but `next-auth` is already pinned to an exact beta (`5.0.0-beta.32`, not a range), so that coupling won't break on an incidental bump — recommended. (2) A gated test-only Credentials provider added to `auth.ts`'s `providers` array — exercises the real Auth.js flow faithfully but leaves a permanent (if env-gated) auth bypass surface in shipped code. (3) A dedicated `/api/test/sign-in` bypass route, gated the same way — same shipped-surface risk as (2), largest blast radius if the gate is ever misconfigured. Cost of adding Playwright: one new devDependency (`@playwright/test`) plus a one-time browser binary download (~150–300MB); the e2e spec itself can only cover "create then join" (T12's stated check) — real progress updates need the T11 poller plus an actual Riot match and are out of scope for a UI e2e test.

**7. Product decisions for the user (not decided here).**
- Personal goals only vs. a group leaderboard/ranking on the view page.
- UI language: Spanish, English, or both (already an open item in `odd/tasks/lol-tft-challenges.md`).
- Whether joining requires an already-linked Riot account first (redirect to `/account`) or the join flow can embed the link form inline.
- Whether a creator auto-joins their own challenge on creation.
- Whether a challenge can be edited or deleted after creation, and by whom.
- Free-text vs Data Dragon-backed champion picker (Q3).
- Which e2e auth-bypass approach to accept (Q6) — a permanent security-relevant addition to a codebase already under active Riot ToS/production-key review.
- Whether `/challenges` (browse) lists public challenges regardless of whether their window is still active, or only currently-active ones.

**8. Size forecast.**
Rough estimate, scaled against T8 (repository adapter, ~similar order) and T10 (Riot ID linking: port + adapter + use case + 3 UI files): domain/application/adapter layer (new use cases, new port method, new repository methods, their tests) ≈ 500–700 changed lines; UI routes (3 routes × page/actions/client-component trio, the rule builder being the heaviest single piece) ≈ 600–900 lines; Playwright harness (install, config, auth fixture, one create-then-join spec) ≈ 150–300 lines. Total ≈ 1300–1900 changed lines — 3–5× the 400-line review budget. Recommended chained-PR slices (each with clear scope, its own Vitest coverage or manual/e2e check, matching the Feature Branch Chain pattern already used for T9→T10→T11 stacked branches):
1. Repository/port additions (`listPublic`, batch progress read, `RiotAccountRepository.findById`) + tests — ~200–350 lines, no UI.
2. Application use cases (`createChallenge`, `joinChallenge`, `getChallengeView`, `listPublicChallenges`) + tests — ~250–400 lines, depends on (1).
3. Create-challenge route + rule-builder client component — ~350–500 lines, the heaviest UI slice.
4. Browse + view/join routes — ~300–450 lines.
5. Playwright install/config + auth fixture + the create-then-join spec — ~150–300 lines, depends on slices 3–4 being deployable together.

## Approaches — E2E auth strategy (the one real technical fork)

| Approach | Pros | Cons | Effort |
|---|---|---|---|
| Session-cookie injection (mint Auth.js JWT in test harness) | Zero production code change; all risk in test fixture; `next-auth` pinned to exact beta version so no silent breakage | Coupled to next-auth's cookie/JWT encoding internals | Low-Medium |
| Gated test-only Credentials provider | Exercises the real Auth.js flow end-to-end | Permanent (if gated) auth surface shipped in `auth.ts` | Medium |
| Gated `/api/test/sign-in` bypass route | Simplest Playwright call | Largest blast radius if the env gate is ever misconfigured; explicit bypass endpoint in shipped code | Low |

## Recommendation

Build the three routes on the existing account-page pattern (server page + server actions + one client form with `useActionState`), reuse `rule-codec.ts`'s `parseRules` verbatim for rule-builder validation instead of inventing a parallel schema, add the small set of missing port methods (`listPublic`, a batch progress read, `RiotAccountRepository.findById`) before the use cases that need them, and use session-cookie injection for Playwright auth to avoid adding any permanent bypass surface to a codebase already under Riot ToS review. Slice delivery into the 5 PRs above under the auto-chain delivery strategy given the 400-line budget.

## Risks
- Estimated total size (1300–1900 lines) is 3–5x the review budget; skipping the chained-PR slicing recommendation risks an oversized single PR.
- No champion allow-list exists anywhere in the codebase; free-text champion criteria can silently create an unwinnable rule with no validation feedback until evaluation.
- `findProgress`/`RuleProgress` currently strip the `progress.updatedAt` timestamp that exists in the DB; reusing `poll_state.last_polled_at` instead is a workaround, not a data-accurate "when was this specific rule last evaluated."
- Two of the three e2e-auth options leave a permanent, env-gated authentication surface in shipped code, which is a real security review burden for this project — the safest option is also the most version-coupled.
- The hybrid artifact store's OpenSpec write for this exploration could not be completed by the exploration sub-agent (no file-write tool); this file was persisted by the orchestrator from the Engram observation.

## Ready for Proposal
Yes. The domain/port/adapter gaps are small and well-scoped (3 new port methods, 4 new use cases), the UI pattern to extend already exists and works (`/account`), and the one genuinely open technical fork (e2e auth strategy) has a clear recommendation. The product decisions in Q7 should be resolved (or explicitly deferred) before or during `sdd-propose`, since at least two of them (auto-join, edit/delete) change what `createChallenge`/`getChallengeView` need to do.
